# Supabase 저장 분석

[README로 돌아가기](../README.md) · [서버 운영](deployment.md#supabase-저장소-확인) · [AI 호출 기록](ai.md#ai-호출-기록-supabase-회원-모드)

2026-11-03 연결된 DB를 `BEGIN READ ONLY`로 조사했다. 아래 수치는 조사 시점의 스냅샷이며 계속 바뀐다. `.env`로 선택된 실행 방식은 `supabase` 회원 로그인 + `local` 설치다. DB에 합성 활동을 쓰거나 마이그레이션을 적용하지 않았다. 테스트는 별도의 합성 HTTP 저장소에서 실행했다.

## 어느 경로로 연결하는가

브라우저는 앱의 `/api`만 호출한다. Hono 인증에서 Supabase `/auth/v1/user`와 `vt_members`로 사용자·권한을 확인한 뒤, `CloudRuntime`이 UUID별 서비스·작업 큐·캐시를 선택한다. `WikiStorage`의 상대 파일 경로를 `CloudStorage`가 `key`로 바꾸어 Supabase Data API에 보낸다. 각 요청에는 공개 키와 검증한 회원의 JWT를 넣고 사용자별 RLS를 적용한다. 브라우저에 관리자 DB 암호를 전달하지 않는다.

| 저장 대상 | 읽는 곳·쓰는 조건 | 실제 연결 |
|---|---|---|
| `public.vt_members` | 인증마다 본인 회원 조회. 가입 트리거로 추가, 관리자의 승인·OS 계정 연결은 SQL RPC | `auth/supabase.ts`, `routes/start.ts`, 최초 마이그레이션 |
| `public.vt_documents` | 설정·위키·분석 결과 조회와 upsert. 키는 아래 표 참고 | `cloud/storage.ts` → `/rest/v1/vt_documents`, PK `(user_id,key)` |
| `public.vt_events` | 학습 이벤트·질문 기록을 조회하고 POST 활동 뒤 추가 | `cloud/storage.ts` → `/rest/v1/vt_events`, `(user_id,key,seq)` 인덱스 |
| `public.vt_locks` | 짧은 저장 작업 전 잠금 획득, 종료 시 삭제. AI 실행 중에는 잡지 않음 | `vt_lock`·`vt_unlock` RPC |
| `public.vt_ai_calls` | 실제 AI 요청마다 성공·오류·취소 기록을 추가. 앱 회원은 조회 불가 | 제공자 → `CloudAiLog.call`, `/rest/v1/vt_ai_calls` |
| `public.vt_ai_runs` | AI 작업의 최종 상태·결과물을 추가. 앱 회원은 조회 불가 | `withAiRun` → `CloudAiLog.run`, `/rest/v1/vt_ai_runs` |
| `public.vt_ai_run_usage` | 위 두 AI 표에서 계산하는 관리자용 뷰. 직접 저장하는 표가 아님 | 두 번째 마이그레이션의 집계 뷰 |
| `vibe_teacher.memory_migrations` 및 mem0 검색 표 | 기존 비회원/홈 토큰 모드에서 mem0를 선택하고 DB·AI 키를 설정한 후 색인할 때 | `memory/database.ts`·`mem0.ts`의 직접 PostgreSQL 연결. 회원 모드에서는 사용하지 않음 |

Supabase `local`은 저장 위치가 로컬이라는 뜻이 아니다. 원본 대화와 소스 파일을 현재 기기에서 읽고, 회원 데이터는 Supabase에 저장한다. 로그인 방식을 지정하지 않은 기존 비회원/홈 토큰 모드는 파일 저장소를 쓴다. 예전 파일이 자동 업로드되지는 않는다.

| 문서/원장 상대 키 | 내용과 생성 조건 |
|---|---|
| `learners/<id>/prefs.json`, `onboarding.json` | 설명 난이도 선택, 시작 단계 저장 |
| `projects/<p>/repo/current.json`, `materials.json`, `history.json` | 레포 위키 생성·업데이트의 자료와 이력 |
| `projects/<p>/repo/text/<level>.json` | 읽는 수준별 레포 설명. 생성 실패 사유도 문서로 남김 |
| `projects/<p>/repo/features/<feature>.<level>.json`, `index.<level>.json` | 주요 기능 분석과 분석 완료 시각 |
| `enrich/<hash>.json` | 세션 AI 요약·개념 분석. 레포 위키와 별도의 생성 기능 |
| `projects/<p>/sessions/<hash>.json`, `snapshots/<revision>.json`, `ai/<revision>.<level>.json` | 세션 위키의 현재 판·내용·AI 문장 |
| `learners/<id>/events.jsonl` | 이해 상태·설명 방식 선택·학습 활동. `vt_events`로 추가 |
| `learners/<id>/projects/<p>/help.jsonl` | 도움 질문의 대기·완료·실패 상태. 같은 질문의 최신 행을 선택 |
| `learners/<id>/profile.json`, `concepts.json` | 원장에서 계산한 프로필과 접한 개념. 학습·질문 활동에 따라 저장 |
| `learners/<id>/knowledge-text.json` 등 | 내 지식 설명을 생성할 때 저장하는 수준·사실 지문별 문장 |
| `learners/<id>/knowledge-views/<hash>.json` | 재방문에 먼저 표시할 마지막 목록. 현재 학습 상태는 원장에서 다시 읽으며 단순 조회로 학습 이벤트를 만들지 않음 |

원본 세션 JSONL과 전체 소스 파일은 Supabase에 그대로 복제하지 않는다. AI 요청에 실제 포함된 마스킹된 요약·코드 발췌는 AI 호출 기록에 저장된다.

## 실제로 얼마나 저장하고 읽었는가

DB 통계 초기화 시각은 `2026-10-29 21:49:05 KST`였다. 현재 행 수는 정확한 `COUNT(*)`, 나머지는 그 시각 이후 DB 누적 통계다. 스캔 수는 HTTP 요청 수·읽은 행 수와 다르며 관리자·다른 기기의 요청도 섞일 수 있다.

| 표 | 현재 행 | 순차 스캔 | 인덱스 스캔 | INSERT 행 | UPDATE 행 | DELETE 행 |
|---|---:|---:|---:|---:|---:|---:|
| `vt_members` | 2 | 29 | 1,190 | 3 | 4 | 1 |
| `vt_documents` | 13 | 13 | 2,310 | 18 | 8 | 5 |
| `vt_events` | 0 | 7 | 16 | 0 | 0 | 0 |
| `vt_locks` | 0 | 10 | 29 | 10 | 0 | 10 |
| `vt_ai_calls` | 26 | 14 | 5 | 26 | 0 | 0 |
| `vt_ai_runs` | 5 | 10 | 3 | 5 | 0 | 0 |
| `memory_migrations` | 1 | 4 | 0 | 2 | 0 | 1 |

문서 13행은 레포 관련 10행, 설명 수준 설정 2행, 시작 설정 1행이다. `pg_column_size(value)` 합계는 레포 약 189KB이며 테이블·인덱스 전체 디스크 크기나 전송량과 다르다. AI 호출 26행은 레포 위키 14회(성공 10·오류 4), 주요 기능 12회(성공 10·오류 2)다. AI 작업 5행은 성공 4·오류 1이다. 오류 호출이 있어도 보조 확인 실패 후 이어 쓰기나 재시도가 성공하면 작업은 완료될 수 있다.

### 비어 있는 곳의 원인

- **`vt_locks` 0행은 정상**이다. 누적 INSERT 10·DELETE 10이므로 잠금을 사용한 뒤 해제한 흔적도 확인된다. 상시 보관할 데이터가 아니다.
- **`vt_events`에는 성공한 추가 기록이 없다.** 현재 문서와 AI 기록은 시작 설정·레포 위키·기능 분석에 한정되고, 이 기능들은 학습 원장을 추가하지 않는다. 따라서 학습 피드백·질문 기능 미사용으로 설명된다. 코드 경로와 실제 사용 흔적을 대조한 추론이며 실패한 모든 요청의 부재까지 증명하지는 않는다. 합성 회원 모드 HTTP 회귀 검사에서는 학습 피드백 → 이벤트 1행·프로필 저장, 동일 요청 재시도 시 추가 0행, 타 계정 거절을 확인했다.
- **세션 요약·세션 위키·학습 프로필 문서의 부재**도 해당 기능을 생성·사용해야 저장하는 구조와 맞는다. 레포 기능 페이지를 만드는 것만으로 세션별 요약이나 이해 상태가 생기지 않는다. GET에서 AI를 자동 호출하지 않는다.
- **mem0 데이터 표가 없는 것은 회원 모드 정책과 맞는다.** `createWikiServices`는 클라우드 저장소가 있으면 기억 백엔드를 `local`로 지정해 Supabase의 공유 원장을 키워드로 검색한다. 관리자 DB 주소가 있어도 회원 모드에 mem0 색인을 만들지 않는다. 남아 있는 `memory_migrations` 1행은 검색 기억 데이터가 아니라 SDK 스키마 관리용이다.
- **`vt_ai_run_usage`는 뷰**라서 저장 행이 독립적으로 쌓이지 않는다. 회원 토큰으로 AI 로그를 SELECT할 수 없는 것도 정답 보호를 위한 의도된 권한이다. 관리자 SQL 조회로 확인해야 한다.

현재 확인한 상태만으로 저장 장애가 있다고 판단할 근거는 없다. AI 로그 저장 실패는 결과 생성을 중단시키지 않는 기존 정책이 있으므로 향후에는 설정의 실패 수와 서버 `[ai-log]` 경고, 마이그레이션 존재 여부도 함께 본다.

## 느려지는 경로와 반영한 개선

기존에는 화면 API마다 인증·회원 조회가 붙었고, 문서마다 HTTP 왕복을 만들었다. `getCached(...,'any')`는 수준 4개 × 제공자 2개의 후보 파일을 순서대로 찾았다. 최대 60개 세션을 모으는 레포 위키와 최대 40개를 보는 내 지식·계정 요약도 세션마다 기다렸다. 관련 문서 3개를 저장할 때는 upsert도 3번 했다.

| 경로 | 현재 동작 |
|---|---|
| 동시 인증 | 같은 토큰의 진행 중인 조회만 합침. 다음 API에서는 사용자·회원 권한을 다시 확인 |
| 문서 읽기 | 동시 키를 최대 40개/URL 예산으로 묶어 조회. 합성 테스트에서 80문서가 2 HTTP 요청 |
| 중복·재방문 | 같은 읽기는 진행 중 요청을 공유하고, 문서 부재도 5초간 재사용 |
| 메모리 한도 | 서버 사용자별 256항목/8MiB, 브라우저 150항목/8MiB. 디스크 캐시로 개인 응답을 남기지 않음 |
| 세션별 IO | 레포·내 지식·계정 요약·기능의 관련 세션을 최대 6개씩 병렬 처리. 입력 순서·권한 검사 보존 |
| 원장 | 첫 조회는 500행씩 읽고, 다음에는 마지막 seq 이후 행만 확인. 추가·잠금 뒤에는 반드시 최신 행을 조회 |
| 문서 쓰기 | 레포 자료 3개, 세션 snapshot+인덱스, 기능 페이지+인덱스를 각각 한 배열 upsert로 저장 |
| 브라우저 | GET 메모리 캐시와 진행 중 요청 공유. 쓰기·인증 변경·작업 완료 후 무효화. 명시적 새로고침은 캐시 우회 |
| 캐시 정확성 | 수정용 문서는 잠금 안에서 새로 조회. 쓰기와 겹친 예전 읽기가 완료돼도 캐시에 다시 넣지 않음. 반환 객체 복제 |
| 작업 표시 | 실제 AI/읽기/쓰기 단계, 단계 기준 예상 진행률. 레포 위키는 자료 수집부터 저장까지 같은 작업으로 표시 |

문서 일괄 저장은 PostgREST의 [배열 upsert](https://docs.postgrest.org/en/stable/references/api/tables_views.html#upsert)를 사용한다. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)와 기존 표·정책을 유지하므로 새 마이그레이션은 없다. AI 요청 기록은 매 호출마다 계속 저장하며, 기록을 비동기로 버리거나 로그를 생략해 속도를 높이지 않았다. 서로 의존하는 AI 후속 질문은 병렬화하지 않는다.

실측한 것은 DB 스냅샷과 합성 경계 테스트의 요청 수다. 운영 환경의 화면 로딩 시간·AI 응답 시간 개선 배수는 아직 측정하지 않았다. 다른 기기의 문서 변경을 다시 조회할 때 서버·브라우저의 각 5초 캐시를 모두 거치면 약 10초의 지연이 생길 수 있다. 열린 화면은 자동 갱신하지 않는다. 수정용 읽기는 이 캐시를 우회한다. 앱의 테이블별 시간 합계에는 병렬 요청의 시간도 각각 포함된다.

## 다시 확인하기

재방문 때 한동안 목록이 비어 보이고 AI 작성 뒤 다시 나타나는 경로도 점검했다. 이전에는 매번 세션을 다시 모은 뒤 목록을 표시했고, 사실 지문이 바뀌면 이전 설명을 비운 채 자동 작성을 기다렸다. 현재는 저장된 목록을 먼저 보여 주면서 최신 조회를 병렬로 진행한다. 최신 조회가 끝난 뒤에만 필요한 AI 작성을 시작하며, 동일한 사실·수준의 재방문은 기존 설명을 재사용한다. 보기 캐시에는 현재 계정 권한·읽는 수준·선택 범위를 포함하고 학습 상태는 현재 원장을 적용한다. 같은 목록은 다시 저장하지 않는다.

관리자 DB 연결 설정 후 `npm run cloud:inspect`를 실행한다. 스키마를 만들거나 수정하지 않고 행 수·RLS·누적 통계·문서 종류·AI 기능별 상태만 출력한다. 실시간 본인 요청 수는 **설정 → 내 저장소 활동** 또는 인증한 `/api/me/storage`에서 확인한다. 이 통계는 저장소 클라이언트 범위이며 인증·회원 관리 요청과 다른 사용자 데이터는 포함하지 않는다.

검사는 `npm run typecheck`, `npm test`, `npm run build`로 실행한다. 캐시 만료·기기 간 잠금·쓰기 경합·페이지 경계·사용자 분리·실패 재시도·AI/저장 단계·완료/취소 표시를 합성 데이터로 검증한다. 실제 DB 쓰기·실제 AI 호출은 이 검사에서 하지 않는다.
