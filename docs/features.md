## 앱 안의 사용 방법

위쪽 메뉴의 **사용 방법**(`/guide`)은 쓰는 사람 입장에서 화면별 버튼과 기능이 하는 일, 언제 쓰면 좋은지를 모은 안내입니다. 위쪽 메뉴에서 **시작하기** 바로 옆에 있고, 시작 안내를 마친 화면 맨 아래의 **사용 방법 보기**로도 열 수 있습니다. 여는 것만으로 AI를 부르거나 기록을 저장하지 않습니다.

안내는 **지금 로그인한 계정에서 보이는 메뉴와 버튼만** 보여 줍니다.

| 항목 | 안내가 보이는 사람 |
|---|---|
| 소스 설정 | 이 설치를 관리하는 사람 (노트북 설치 소유자 등) |
| 키 저장 (OpenRouter 키 입력) | 노트북 설치에서 화면으로 키를 넣을 수 있는 사람 |
| 계정 선택 칸 · 계정 카드 | 볼 수 있는 계정이 둘 이상일 때 |
| 로그아웃 | 로그인해서 쓰는 사람 |
| 학습 기록을 볼 수 있는 사람 (자주 묻는 질문) | 이메일 회원으로 로그인한 사람 |
| 승인 상태 확인 · 승인 대기 질문 | AI 사용 승인을 기다리는 회원 |
| 보낼 내용 미리 보기 (세션 분석) | 기술 정보를 보는 사람 (관리자 또는 설명 난이도 주니어·시니어) |

- **처음이라면 이 순서로 해 보세요**: 설명 난이도 → 시작하기 → 내 프로젝트 → 세션 분석 → 질문·문제 → 레포 위키 → 내 앱 사용 설명서(어떻게 사용하나요?) → 내 지식 순서로 안내하고, 해당 화면으로 가는 링크를 둡니다.
- **버튼이나 기능 이름으로 찾기**: 버튼 이름이나 설명에 들어 있는 말로 항목을 거릅니다(예: `알고 있어요`, `업데이트`). 절 제목과 맞으면 그 절 전체를 보여 줍니다.
- **화면별 절**: 위쪽 메뉴, 시작하기, 내 프로젝트, 프로젝트 화면, 레포 위키, 주요 기능 페이지, 어떻게 사용하나요?(내 앱 사용 설명서), 세션 화면, 세션 분석 문서, 도움 패널, 문제 풀기, 내 지식(상태 배지 포함), 설정. 항목마다 버튼 이름 → 하는 일 → **이렇게 써 보세요** 순서로 적고, 맨 위 목차에서 각 절로 이동합니다.
- **자주 묻는 질문**: AI에 보내는 범위, 읽기 전용, 저장된 결과 재사용, 틀린 답과 `모르겠어요`의 처리, 승인 대기(대기 중일 때만), 생성 실패, 기록이 보이지 않을 때, 내 앱의 사용 설명서 만들기, 학습 기록을 볼 수 있는 사람(회원 로그인일 때만).

회원 관리·서버 설정 같은 운영자 기능은 다루지 않습니다. 운영자 안내는 [공용 서버 가이드](deployment.md)를 보세요.

## 시작하기

**시작하기**에서 아이디어 탐색·방향 정리·기능 구체화·기존 저장소 중 현재 준비 단계를 고르면 다음 할 일과 AI에게 보낼 첫 요청을 받습니다. 시작 안내 맨 아래의 **사용 방법 보기**는 [앱 안의 사용 방법](#앱-안의-사용-방법)을 엽니다. 노트북 설치에 OpenRouter 키가 없으면 시작 화면에 키 입력 칸이 나옵니다. 저장한 키는 화면에 다시 보여 주지 않으며 **소스 설정 → 설명을 작성할 AI**에서 바꾸거나 지울 수 있습니다. 기록은 계정(홈 디렉터리) › 프로젝트(작업 폴더) › 세션 순서로 탐색합니다. **내가 쓴 메시지**와 **만들어진 것**에서 직접 입력한 요청과 파일·명령·패키지·커밋 등의 작업 기록을 확인합니다. 지원 도구와 기본 경로는 [읽는 위치](configuration.md#읽는-위치-기본값)에 있습니다.

## 프로젝트와 세션 묶기

같은 계정에서 여러 도구가 **같은 실제 폴더**를 가리키면 하나의 프로젝트로 모읍니다. 심볼릭 링크 때문에 기록된 경로가 달라도 실제 경로를 확인해 세션을 합칩니다. 이름이 같아도 다른 폴더이거나 다른 계정이면 별개로 유지하며, 없거나 읽을 수 없는 폴더는 기록된 경로를 사용합니다. Git 원격 주소가 같아도 별도로 복제한 폴더나 worktree는 자동으로 합치지 않습니다.

업데이트 후 서버를 다시 시작하고 브라우저를 새로고침하면 통합된 목록을 볼 수 있습니다. 예전 프로젝트 링크도 대표 프로젝트로 연결됩니다. 양쪽에 저장한 세션 위키·AI 설명·질문 기록·레포 위키 갱신 이력을 함께 읽으며, 레포 위키는 가장 최근 판을 보여 줍니다. 예전 저장 파일은 보존하고 새 기록은 대표 프로젝트에 저장합니다. 통합 후 레포 위키에 새 세션 안내가 뜨면 **업데이트**를 눌러 합쳐진 세션을 반영합니다.

## AI로 만드는 위키와 개념 카드

개념 사전·키워드 점수·고정 문항 은행을 사용하지 않습니다. AI가 세션의 요청·변경 코드·도구 결과를 읽고 지금 이해하거나 판단하는 데 필요한 개념과 설명 순서를 선정합니다. 처음 보는 프레임워크나 라이브러리도 새 개념 카드로 만들 수 있습니다.

코드는 원본 파일·명령·코드 연결을 수집하고 출처 참조와 데이터 형식을 검사합니다. 프로젝트 사실, 에이전트의 완료 보고, AI의 해석을 구분합니다. 출처가 연결됐다는 사실만으로 내용이 옳다고 검증된 것은 아닙니다.

## 세션 (대화 기록) 분석

코딩 에이전트와 내가 한 대화 기록을 분석하여 이번 대화에서 한 작업, 내가 알면 좋은 개념, 보안 및 취약점 관련 주의사항을 설명 문서로 만듭니다. 세션 화면의 탭은 **세션 (대화 기록) 분석 → 내가 쓴 메시지 → 만들어진 것** 순서입니다. 분석 문서는 **작업 요약 → 작업 설명과 확인할 사항 → 알아둘 개념 → 내 지식 → 보안 점검** 순서로 읽고, 맨 위 목차에서 각 절로 바로 이동합니다.

**분석 시작**을 누르면 작업 요약과 작업·개념·보안 분석을 함께 시작합니다. AI가 기록에서 확인한 사실·주의사항·개념·학습 카드·선행관계를 작성합니다. 개념 카드에는 정의와 이번 작업에서 필요한 이유, 실제 기록의 근거가 표시됩니다. 고정 사전의 개념으로 범위를 제한하지 않습니다. 기반 문서가 없거나 기록이 바뀌었으면 함께 갱신합니다.

분석 문서는 `/sessions/<세션 키>/analysis` 주소로 다시 열 수 있습니다. 기존 세션·탭 주소도 유지합니다. 프로젝트의 레포 위키에는 **대화 기록 분석 문서** 트리가 표시되며, 문서 제목과 하위 절(작업 요약·작업 설명·알아둘 개념·보안 주의사항)을 눌러 이동합니다. 저장된 결과가 생기면 레포 위키를 다시 생성하지 않아도 목록에 연결됩니다. 요약만 있으면 **일부 분석 결과**로 표시하고, 생성 중인 빈 문서는 완료 문서로 표시하지 않습니다. 목록을 읽는 것만으로 AI를 호출하거나 원본 대화를 다시 읽지 않습니다.

분석에서 나온 개념은 **내 지식 위키**에도 연결됩니다. 각 개념의 **이 개념이 나온 대화 분석**에서 원래 분석 문서의 해당 개념으로 이동하고, 관련 프로젝트 위키도 열 수 있습니다. 네 번째 이후 출처는 **관련 분석 문서 더 보기**를 펼쳐 모두 확인합니다. 분석 문서에서도 프로젝트 위키와 해당 프로젝트의 내 지식으로 돌아갈 수 있습니다.

이미 저장된 같은 기록·설명 난이도의 결과는 재사용합니다. **다시 분석하기**로 새로 작성하거나 진행 중 작업을 취소할 수 있습니다. 현재 AI 제공자, 전송 내용·미리 보기, 모델·소요 시간·요금 등의 기술 정보는 **관리자**, 또는 설명 난이도를 **개발 용어에 익숙해요 / 핵심만 자세하게**로 선택한 사용자에게 표시합니다. 첫 분석 전에도 요약과 작업·개념·보안 분석 양쪽의 전송 내용을 미리 볼 수 있으며, 미리 보기는 문서를 저장하거나 AI를 호출하지 않습니다. AI 설정 변경은 기존 관리자·설치 소유자 권한을 따릅니다.

**만들어진 것** 탭은 **에이전트가 정리한 작업 결과**를 먼저 보여 줍니다. 요청마다 내가 요청한 내용과 에이전트가 작업 뒤에 남긴 답변 원문을 함께 읽습니다. 마지막 보고는 펼쳐 두고 이전 요청은 눌러서 확인합니다. 답변은 300자·4,000자 제한 없이 전체를 표시하며 제목·목록·코드·표·문서 링크를 읽기 좋게 보여 줍니다. **텍스트 원문 보기**에서 기록에 남은 문장도 그대로 확인할 수 있습니다. Codex의 진행 알림과 최종 답변은 구분하며, 결과 답변이 없는 요청에는 그 상태를 표시합니다. 파일 변경·명령·패키지·커밋은 아래 **파일·명령 등 작업 기록**을 펼쳐 확인합니다. 화면에서 원문 전체를 읽어도 AI에는 기존처럼 길이를 제한하고 비밀값을 가린 발췌만 보냅니다.

**보안·데이터 주의사항**도 AI가 기록의 근거를 보고 선정합니다. 공통 체크리스트를 모든 프로젝트에 붙이지 않습니다. 실제 서비스 환경이나 전체 저장소의 취약점을 검사했다는 뜻은 아닙니다. AI가 제시한 확인 사항과 읽지 못한 범위를 함께 확인하세요.

## 레포 위키

프로젝트 화면의 큰 탭은 **프로젝트 안내 (레포 위키) → 세션 (대화 기록) → 이 프로젝트와 관련된 내 지식** 순서입니다. 레포 위키 안의 탭은 **어떤 프로젝트인가요? → 주요 기능 → 어떻게 동작하나요? → 어떻게 사용하나요? → 보안 및 취약점 점검** 순서입니다.

프로젝트의 **레포 위키 만들기**를 누르면 README, 의존성, 실행 스크립트, 주요 코드 발췌와 세션 요약을 AI에 전달합니다. AI가 사용자 중심 페이지와 동작 중심 페이지의 절 구성·제목·설명·주의사항을 작성합니다.

레포 위키 화면 위의 **대화 기록 분석 문서**에서 이 프로젝트의 분석 문서를 트리로 찾아갑니다. 레포 위키 본문이나 주요 기능의 세션 근거도 해당 대화 분석 문서로 이어집니다.

스크립트·API 경로 표, 데이터베이스 표와 코드 연결 그림은 저장소에서 수집한 원문 자료입니다. AI가 이를 인용할 수 있지만 값을 바꾸거나 연결을 만들어낼 수는 없습니다. 같은 그림·표·코드는 한 페이지에 한 번만 표시하며, 이미 만들어진 위키에서도 다시 생성하지 않고 중복이 사라집니다. 근거를 펼쳐 파일 원문과 줄 번호를 확인할 수 있습니다. 코드는 언어(JS·TS·Python·JSON·셸)에 맞춰 문자열·주석·키워드 등에 색을 입혀 보여 줍니다. 스캔은 읽기 전용이며 코드를 실행하지 않습니다.

API 표는 **방식 → 경로 → 동작 설명 → 파일** 순서로 표시합니다. AI가 경로별 코드 발췌를 읽고 무엇을 조회·저장·응답하는지, 확인된 접근 검사는 무엇인지 설명합니다. 발췌만으로 알 수 없는 동작은 확인 범위를 함께 적습니다. 기존 위키는 **업데이트**하면 새 설명 열이 반영됩니다. 8줄이 넘는 표는 기본으로 접어 두고 **API 목록 보기 (경로 N개)**·**스크립트 목록 보기 (N개)**를 눌러 펼칩니다.

**데이터베이스 표**는 **어떻게 동작하나요?** 페이지에 실립니다. 맨 위 요약 표에서 **표 → 저장하는 내용 → 쓰는 주요 기능**을 한눈에 보고, 기능 이름을 누르면 그 기능 페이지로 이동합니다. 표 이름을 누르면 아래의 표별 상세가 펼쳐지며 **컬럼 → 타입 → 조건 → 들어가는 내용**과 이 표를 쓰는 기능마다 무엇을 저장·조회·수정·삭제하는지, 정의 위치와 코드에서 쓰는 줄을 보여 줍니다. 표가 4개 이상이면 표별 상세는 접어 둡니다.

| 읽는 정의 | 예 |
|---|---|
| SQL 마이그레이션 (`*.sql`) | `CREATE TABLE`·`ALTER TABLE`(컬럼 추가·삭제·이름 변경, pg_dump식 기본 키·외래 키)·`COMMENT ON`·`CREATE VIEW`. Supabase `supabase/migrations/` 포함 |
| Prisma (`*.prisma`) | `model`·`enum`·관계 필드·`@@map`·`@map` |
| TypeScript·JavaScript | Drizzle `pgTable`·TypeORM `@Entity`·Mongoose `new Schema`·Sequelize `define`/`init`/`createTable`·Knex `createTable`/`alterTable` |
| Python | SQLAlchemy(`__tablename__`·`Column`·`mapped_column`·`Table`)·SQLModel(`table=True`)·Django `models.Model` |

- 표 이름·컬럼·타입·기본 키·필수·기본값·참조·허용 값(CHECK·enum)은 코드에 적힌 그대로 보여 줍니다. 코드에 표 이름이 따로 없는 ORM 모델은 **모델**로 표시하고 실제 표 이름을 추측하지 않습니다. 컬럼 주석(`-- …`, `COMMENT ON`, `///`, `help_text` 등)은 AI가 설명을 쓸 때 참고만 합니다.
- **코드에서 쓰는 곳**은 서버가 찾습니다: 따옴표 안의 표 이름(`.from('members')`), Supabase REST 경로(`/rest/v1/members`), SQL 문(`FROM members`), 정의 파일을 불러오는 파일의 모델 이름, Prisma의 `prisma.user.findMany` 같은 접근자. SQL 마이그레이션의 함수(`CREATE FUNCTION`, Supabase RPC)가 본문에서 쓰는 표도 모아, 코드에서 그 함수를 부르는 줄(`.rpc('approve_member')`, `/rest/v1/rpc/approve_member`)을 그 표의 쓰는 곳으로 보고 표별 상세에 **SQL 함수**로 함께 보여 줍니다(다른 함수를 거쳐 쓰는 표는 세 단계까지). 표가 공용 코드(예: 저장소 클래스) 안에서만 쓰이면, 그 코드의 함수를 다른 파일에서 부르는 줄(`storage.readJson(…)` 등)도 서버가 구문으로 찾아 쓰는 곳에 더합니다(같은 파일 안에서 세 단계까지 따라가고, 파일마다 한 줄, `get`·`list` 같은 흔한 이름은 따라가지 않음). 그래서 여러 기능이 함께 쓰는 저장 표도 실제로 저장하는 기능과 이어집니다. 표 이름을 셋 이상 늘어놓은 줄(설치·점검 스크립트의 표 목록)은 맨 뒤로 미룹니다. 표마다 최대 16줄을 보여 줍니다.
- 저장하는 내용·컬럼별 값·쓰는 기능 설명은 AI가 씁니다. 자료에 있는 표와 컬럼, 지금 위키의 주요 기능만 받으며, 그 표의 정의·SQL 함수·쓰는 줄이 있는 파일을 근거로 인용한 설명만 싣습니다. 여러 기능이 함께 쓰는 저장 모듈을 거쳐 쓰는 표는 그 모듈의 쓰는 줄과 기능 쪽 호출 코드를 함께 인용해 연결합니다. AI가 기능을 고르지 않았어도 기능 파일에서 그 표를 쓰는 줄이 보이면 "코드에서 확인한 연결"로 표시합니다(설명 문장 없음).
- 설명이 빠진 표가 있으면 표 자료만 다시 보내 설명을 받습니다.
- 로그인·회원 승인·잠금·AI 호출 기록처럼 주요 기능이 아니라 여러 기능을 받치는 표는 **공통 기반**으로 표시하고, 그 이유를 근거와 함께 보여 줍니다. 공통 기반 표는 주요 기능과 잇지 않아도 됩니다.
- 코드에서 쓰는 곳이 있는데 **어떤 주요 기능과도 이어지지 않고 공통 기반도 아닌 표**가 있으면 연결을 다시 묻습니다. 전체 자료를 다시 보내지 않고, 표마다 **"이 표는 지금 주요 기능 중 무엇과 관계가 있나요?"** 라는 짧은 질문을 만들어 한 번에 묻습니다(Claude CLI를 쓰면 가벼운 `haiku` 모델, 아니면 OpenRouter). 질문에는 서버가 읽은 그 표를 쓰는 줄 앞뒤 몇 줄(표마다 최대 3곳, 모두 합쳐 24,000자 이내), 그 파일을 불러오는 파일, 지금 주요 기능 목록만 들어갑니다. AI는 자연어로 짧게 답하고 관계있는 기능이나 공통 기반을 고릅니다. 주요 기능을 따로 묻지 못했을 때만 그 표를 쓰는 사용자 기능을 새로 더할 수 있습니다(최대 16개 안에서). 근거를 확인한 연결만 싣습니다.
- 그래도 기능과 잇지 못한 표는 위키 경고에 알리고, 표별 상세에 AI가 답한 내용(예: "특정 기능이 아니라 모든 저장이 거치는 잠금입니다")을 근거와 함께 보여 줍니다. 표·컬럼 원문은 그대로 보여 주고, 코드에서 쓰는 곳을 찾지 못한 표는 그 이유를 따로 표시합니다. AI가 표를 넣을 절을 고르지 않으면 동작 페이지 끝에 **데이터베이스 표** 절로 싣습니다.
- 정의 파일은 읽기만 하며 테스트 폴더와 되돌리기(`down.sql`) 마이그레이션은 읽지 않습니다. SQL·Prisma 파일은 최대 80개, 표는 최대 80개·표마다 컬럼 60개까지 담고 넘으면 일부만 읽었다고 표시합니다. 이전 위키는 **업데이트**를 누르면 표가 생깁니다.

코드 연결 그림의 각 상자에는 파일명과 함께 **이 파일이 실제로 하는 일**을 표시합니다. AI가 코드 근거로 프론트엔드·백엔드의 분리를 확인하면 큰 영역을 나눠 그리고, 함께 쓰는 코드는 공통 영역에 둡니다. 화살표는 실제 코드의 파일 참조 관계이며 실행 순서나 통신을 추측해 추가하지 않습니다. Python은 `from . import rows`·`from .steps import load`처럼 하위 모듈을 가져오는 형태도 실제 파일이 있으면 연결로 읽습니다. 상자 맨 위에는 시작 파일이면 `시작 파일 - index.html`, 나머지는 `main.js`처럼 파일 이름만 표시합니다. 시작 파일에서 연결을 찾지 못한 파일만 모인 폴더(별칭 import·독립 스크립트 등)는 그 폴더의 `__main__.py`·`__init__.py`·`main.py`·`app.py`·`index.ts`·`main.ts`·`index.html` 같은 파일을 그 폴더의 시작 파일로 보고 거기서부터 연결을 그립니다. 상자는 영역마다 왼쪽부터 채웁니다. 라벨과 배치는 저장된 위키에도 바로 적용되며, 폴더별 시작 파일과 열 나누기는 **업데이트** 후 반영됩니다.

AI가 인용한 줄이 실제로 보낸 코드 발췌 밖이면 그 설명은 싣지 않습니다. 겹치거나 맞닿은 발췌를 하나로 합쳐 인용한 것은 받지만, 떨어진 두 발췌 사이의 읽지 않은 줄까지 넓힌 인용은 받지 않습니다. 이런 인용이 있으면 버리기 전에 AI에 **보낸 표시 중에서 다시 골라 달라**고 한 번 짧게 묻습니다(전체 자료를 다시 보내지 않고, 확인하지 못한 표시와 서버가 보낸 후보만 보냅니다).

파일 설명이나 영역이 빠지면 **빠진 파일과 그 파일의 코드 발췌만** AI에 한 번 더 보내 요청합니다. 이미 설명이 붙은 상자는 그대로 둡니다. 모든 상자의 설명과 출처가 연결된 경우에만 생성 완료로 저장하며, 보완에 실패하면 원인을 표시합니다. 이미 설명 없이 생성된 이전 결과는 재사용하지 않으므로 **다시 쓰기**로 새 설명을 받을 수 있습니다.

위키를 작성할 때 AI가 먼저 확인할 질문과 파일 위치를 고르고, 서버가 필요한 코드 일부를 읽어 추가 답변을 받습니다. Claude CLI에서는 이 확인 단계만 **Haiku·low effort**로 실행하며, CLI 실패나 API 제공자 선택 시에는 OpenRouter의 설정 모델(기본 `openai/gpt-6.1-terra`)을 사용합니다. 추가 확인은 최대 6곳·코드 합계 24,000자이며, 비밀값을 가리고 출처가 확인된 답만 위키 작성에 활용합니다. **AI에 보내는 내용 보기**에서 기본 입력과 추가 확인 범위를 볼 수 있습니다.

새 세션이나 파일 변경이 생기면 **업데이트**로 반영합니다. 문장은 읽는 사람 수준별로 저장하고, 같은 입력으로 이미 생성한 결과는 재사용합니다. 생성에 실패하면 사유와 재시도 동작을 표시하며 고정 설명으로 대체하지 않습니다.

## 주요 기능 페이지

레포 위키를 쓸 때 본문보다 먼저 AI에게 **"이 프로젝트 자체의 주요 기능은 무엇이라고 생각하나요?"** 를 따로 묻습니다(Claude CLI를 쓰면 CLI의 기본 모델, 아니면 OpenRouter). AI는 자연어로 답하고, 사용자가 이 프로젝트로 **직접 하는 일** 단위로 주요 기능(최대 16개)을 고르며, 로그인·저장·기록·설정처럼 다른 기능을 받치는 코드는 **공통 기반**으로 따로 적습니다. 데이터베이스 표 이름이나 공용 저장 모듈로 기능을 만들지 않고, 표는 기능이 무엇을 저장하는지 확인하는 근거로만 씁니다.

- 질문에는 README, 실행 스크립트, API 경로, 표를 쓰는 파일, 파일 목록과 함께 **모든 세션의 '만들어진 것'**이 들어갑니다. 세션마다 내 요청·에이전트 보고 앞부분·만들고 고친 파일·커밋·설치한 패키지를 규칙으로 모으며(AI 호출 없음, 이 저장소의 세션 15개에 약 2초), 여러 세션에서 자주 고친 파일을 먼저 보여 줍니다. 붙여 넣은 글과 자동 문맥은 빼고 비밀값은 가립니다. 이 모음은 프로젝트별 `repo/sessions-made.json`에 저장해 두고, 세션 파일이 바뀌지 않았으면 다시 읽지 않습니다.
- 고른 목록이 그대로 위키의 주요 기능이 되고, 본문 작성 AI는 표 연결 등에 이 목록의 id만 씁니다. 질문이 실패하면 경고를 남기고 본문 작성에서 함께 고릅니다.
- **AI에 보내는 내용 보기**에서 이 질문의 입력도 함께 볼 수 있습니다.

README에만 있고 코드에서 확인되지 않는 기능은 고르지 않으며, 제공하지 않은 파일·세션을 인용한 기능은 목록에서 뺍니다. 다시 생성할 때는 이전 기능 id를 알려 같은 기능이 같은 페이지로 이어지게 합니다. 이 목록은 문장 형식이 바뀐 이번 업데이트부터 만들어지므로, 기존 위키는 **다시 쓰기** 또는 **업데이트**를 누르면 생깁니다 (자동 작성이 켜져 있으면 위키를 열 때 다시 씁니다).

- 주요 기능 목록은 하나입니다. **주요 기능** 탭과 **어떤 프로젝트인가요?** 페이지의 주요 기능 블록이 같은 목록을 보여 주며, 기능 카드를 누르면 `/projects/<프로젝트>/features/<기능>` 페이지로 이동합니다. AI는 주요 기능을 사용자 페이지의 별도 절로 다시 나열하지 않고, 목록을 넣을 위치만 고릅니다 (고르지 않으면 첫 절 다음). 세션 화면에도 그 세션과 관련된 기능 페이지 링크가 표시됩니다.
- 탭은 위키를 받을 때 이미 들어 있는 목록으로 바로 그리고, 자세한 분석 여부만 나중에 받아 표시합니다.
- 기능 카드와 기능 페이지에는 그 기능이 쓰는 **데이터베이스 표**(무엇을 하는지·컬럼 이름)를 함께 보여 줍니다. 레포 위키의 데이터베이스 표에서 거꾸로 모은 것이라 자세히 분석하지 않아도 표시됩니다.
- 처음에는 레포 위키가 고른 관련 파일과 세션만 보여 줍니다. **이 기능 자세히 분석받기**를 누르면 아래 순서로 분석합니다 (GET으로 화면을 여는 것만으로는 AI를 부르지 않습니다).
  1. 서버가 기능 파일, 그 파일이 불러오는 파일, 그 파일을 불러오는 파일의 선언·연결과 AI 호출 단서 줄(`openai`, `chat.completions`, `model:` 등)을 모읍니다.
  2. AI가 이 자료를 보고 **확인할 질문과 파일 위치를 직접 만듭니다**. 서버가 그 부분의 코드만 읽어 줍니다.
  3. AI가 읽은 코드로 답하고, 아직 모르는 것(호출하는 곳, 모델 설정, 프롬프트를 조립하는 함수 등)을 **다음 질문으로 다시 만듭니다**. 최대 3단계, 단계마다 6곳, 코드 발췌는 합계 48,000자이며 비밀값은 가립니다. 새로 읽을 코드가 없으면 일찍 멈춥니다.
  4. AI가 페이지를 씁니다: 한눈에 보기, **사용자는 이렇게 씁니다**(단계별 흐름), 관련 파일과 역할, **AI 호출**, AI가 확인한 질문과 답(단계별), 확인하지 못한 것.
- **AI 호출**에는 제공자·SDK, 모델, 응답 처리와 함께 **실제로 AI에 가는 시스템 프롬프트·사용자 프롬프트 문장만** 보여 줍니다. AI는 코드 위치만 가리키고, 서버가 코드를 구문 분석해 요청의 `system`·`user`·`prompt` 값이나 `{ role: 'system', content: … }` 메시지를 찾습니다. 그 값이 가리키는 상수, 불러온 파일, 감싸는 함수(예: `withReader(PROMPT, level)`는 실제 인자를 넣어 펼침)를 따라가 원문을 그대로 이어 붙입니다. 색이 다른 `{…}`는 실행할 때 채워지는 값이고, 문장이 적힌 곳은 링크로 열 수 있습니다. 가리킨 범위에 요청이 여러 개면 줄·호출 이름(`schemaName` 등)과 함께 모두 보여 줍니다. 전체 코드는 접힌 **코드 보기**에서 확인합니다. JS·TS·Python을 지원하며, 프롬프트를 특정하지 못하면 코드를 펼쳐 보여 줍니다. 이 정리는 페이지를 열 때 계산하므로 이미 분석한 기능도 다시 분석할 필요가 없습니다.
- 모델 값은 가리킨 줄에 실제로 적혀 있을 때만 싣고, 확인하지 못하면 "코드에서 확인하지 못함"으로 표시합니다. 근거를 확인하지 못한 단계·파일·답은 거르고 경고로 남깁니다.
- 질문 단계는 로컬 `auto`·`claude-cli` 설정에서 Claude CLI **Haiku·low effort**, 페이지 작성은 Claude CLI의 기본 모델로 실행합니다. CLI 실패나 `openrouter` 설정, 공용 서버에서는 OpenRouter의 설정 모델(기본 `openai/gpt-6.1-terra`)을 사용합니다. 작은 저장소 기준 AI 호출 5번, 1~2분 정도 걸립니다.
- **AI에 처음 보내는 내용 보기**에서 첫 질문 계획 요청의 시스템·사용자 프롬프트를 볼 수 있습니다. 이후 단계의 질문은 AI가 답을 보고 만들며, 회원 모드에서는 모든 요청·응답이 [AI 호출 기록](ai.md#ai-호출-기록-supabase-회원-모드)에 `feature=repo_feature`로 남습니다.
- 분석한 뒤 읽은 파일이 바뀌면 "분석한 뒤 바뀐 것이 있습니다"를 표시합니다. **다시 분석하기**로 갱신하세요. 페이지는 읽는 사람 수준별로 따로 저장합니다.

## 어떻게 사용하나요?

레포 위키의 **어떻게 사용하나요?** 탭은 그 프로젝트를 **실제로 쓰는 사람 입장**의 사용 설명서입니다. 앱 안의 [사용 방법](#앱-안의-사용-방법) 탭을 만든 순서를 AI가 저장소마다 따라 합니다. 화면은 앱의 사용 방법과 같은 모양입니다: **처음이라면 이 순서로 해 보세요** → 화면별 절(버튼 이름 → 하는 일 → **이렇게 써 보세요**) → **자주 묻는 질문**, 그리고 찾기 칸과 목차. 운영자·관리자 화면(회원 관리, 서버·배포 설정, 환경 변수, 개발 명령)은 쓰지 않습니다. 명령줄 도구라면 사용자가 입력하는 명령과 옵션을 안내합니다.

레포 위키를 만든 뒤 탭을 열고 **분석하기**를 누르면 아래 순서로 분석합니다 (탭을 여는 것만으로는 AI를 부르지 않습니다).

1. 서버가 화면·메뉴·명령이 정의됐을 만한 파일을 고릅니다: 화면 문구 파일(`i18n`·`locales`·`messages` 등), 진입점·메뉴(`App`·`Layout`·`routes`·`main`·`cli` 등), 화면 파일(`.tsx`·`.jsx`·`.vue`·`.svelte`·`.astro`·`.html`, `pages`·`components` 폴더), 사용자 문서(`docs/*.md`), `package.json`. 테스트·예제 폴더는 뺍니다. 후보마다 선언과 연결, 버튼·메뉴 단서 줄(`<button`, `onClick=`, `<Route`, `.command(` 등), 문구 파일의 묶음 위치를 모으고 README 앞부분을 함께 보냅니다.
2. AI가 이 자료와 레포 위키의 주요 기능 목록을 보고 **확인할 질문과 파일 위치를 직접 만듭니다**. 서버가 그 부분의 코드만 읽어 줍니다.
3. AI가 읽은 코드로 화면·버튼 이름(화면 문구 그대로), 누르면 일어나는 일, 보이는 조건을 답하고, 아직 모르는 것을 **다음 질문으로 다시 만듭니다**. 최대 4단계, 단계마다 8곳, 코드 발췌는 README를 포함해 합계 160,000자이며 비밀값은 가립니다. 주요 기능 중 아직 화면을 확인하지 못한 것을 먼저 따라갑니다.
4. AI가 안내를 씁니다. 서버는 모든 단계·버튼·질문의 근거가 실제로 보낸 코드 발췌 안에 있는지 검사해 확인하지 못한 것은 거르고, 버튼이 하나도 남지 않은 절은 뺍니다.

- 버튼 이름 아래의 **화면 문구 그대로** 표시는 AI가 옮긴 화면 문구가 인용한 코드에 글자 그대로 있는지 서버가 확인했다는 뜻입니다. 이름과 다른 문구면 `“Save”`처럼 실제 문구를 보여 주고, 코드에서 찾지 못한 문구는 표시를 빼고 경고로 알립니다.
- 항목마다 근거를 펼쳐 파일과 줄을 열 수 있고, 맨 아래 **분석하면서 확인한 것**에서 AI가 만든 질문과 답, 코드로 확인하지 못한 것을 봅니다.
- 질문 단계는 Claude CLI **Haiku·low effort**, 안내 작성은 기본 모델로 실행합니다. CLI 실패나 `openrouter` 설정, 공용 서버에서는 OpenRouter의 설정 모델(기본 `openai/gpt-6.1-terra`)을 씁니다. 회원 모드에서는 모든 요청·응답이 [AI 호출 기록](ai.md#ai-호출-기록-supabase-회원-모드)에 `feature=repo_usage`로 남습니다.
- **AI에 처음 보내는 내용 보기**에서 첫 질문 계획 요청을 볼 수 있습니다. 분석한 뒤 레포 위키를 업데이트했거나 읽은 파일이 바뀌면 "분석한 뒤 바뀐 것이 있습니다"를 표시하니 **다시 분석하기**로 갱신하세요. 안내는 읽는 사람 수준별로 따로 저장합니다(`repo/usage.<수준>.json`).
- 사람마다 다르게 보이는 버튼은 걸러 내지 않고, 설명에 언제 보이는지를 적습니다.

## 내 지식과 이해 확인

**내 지식**은 세션의 AI 개념에 자기보고·문항 응답·질문·설명 방식 선택을 연결합니다. 맨 위 대시보드에는 **알게 된 개념**(문제로 확인·익히는 중), **맞힌 문제**, **아직 안 풀어 본 개념** 수와 알게 된 개념 막대를 보여 줍니다. 대시보드는 AI를 호출하지 않습니다. 예전에 한 질문과 풀어 본 문제는 아래 **내 기억 검색**에서 다시 봅니다. 개념 카드는 이름 옆에 분류(예: 설정, 데이터베이스)를 두고, 그 아래 줄에 내 학습 상태(**익히는 중**, **알고 있어요**, **실력이 늘고 있어요** 등)와 맞힌 횟수, 최근 활동, 원래 세션을 표시합니다. 틀린 문제와 질문 횟수는 저장해 다음 설명을 맞추는 데만 쓰고 화면에는 세지 않습니다. 아직 맞힌 문제가 없으면 **간단히 확인하기**로 짧은 문제를 풀어 보라고 안내합니다. 아직 문제로 확인하지 않은 개념에는 상태 배지를 붙이지 않습니다. 프로젝트·세션 화면에는 그 범위의 활동을 따로 표시하고, 일반 개념 상태와 설명 선호는 다음 세션에도 이어집니다. 상호작용한 개념은 개인 개념 기록에도 보존하므로 최근 40개 세션 조회에서 빠져도 다시 연결할 수 있습니다. 설명 문장은 AI가 이 개념이 내 작업과 어떻게 이어지는지와 지금까지의 진행을 응원하는 말로 작성합니다. 맞힌 문제가 없는데 잘 맞혔다고 하거나, 확인 전인데 잘 안다고 쓴 문장은 버립니다.

다시 방문하면 **저장된 목록과 설명을 먼저 표시**하고 새 세션·활동은 뒤에서 확인합니다. 처음 저장된 목록이 없는 범위는 한 번 목록을 모아야 합니다. AI 작성 중에도 기존 카드와 설명은 유지하며, 이전 설명을 임시로 보여 줄 때는 표시를 붙입니다. 학습 상태가 바뀌면 예전 상태 설명을 재사용하지 않고 현재 활동 내역과 개념 요약을 먼저 보여 줍니다. 같은 사실·설명 난이도이면 AI를 다시 호출하지 않으며, **알고 있어요** 선택·퀴즈 응답·근거 변경 등이 있으면 필요한 설명만 갱신합니다. 단순 재방문이나 목록 캐시 저장은 `vt_events`를 추가하지 않습니다.

**간단히 확인하기**를 누르면 개념 설명과 최근 응답을 참고해 객관식 또는 OX 문항을 생성합니다. 정답과 해설은 제출 전 브라우저로 보내지 않고 서버에서 채점합니다. AI가 만든 문항도 처음 풀고 도움 패널 없이 낸 응답이면 개념 상태에 반영합니다. 건너뛰기와 모르겠어요는 오답이 아닙니다.

**알고 있어요**를 누르면 바로 기록하지 않고 OX 문제 하나로 확인합니다. 맞히면 **알고 있어요**로 기록하고, 틀리거나 건너뛰면 기록하지 않습니다. 내 지식·도움 패널·세션 분석의 **알고 있어요**가 모두 같습니다.

| 상태 | 조건 |
|---|---|
| (배지 없음) | 아직 맞힌 문제가 없거나 OX 문제 하나만 맞힘 |
| 익히는 중 | 고르기 문제 1개, 또는 서로 다른 문제 2개를 맞힘. 또는 **알고 있어요** OX 확인 문제를 처음에 도움 없이 맞힘 |
| 문제로 확인했어요 | 서로 다른 문제 2개 이상을 맞혔고 그중 적용 고르기 문제가 있음 |
| 다시 연습 중 | 맞힌 문제와 틀린 문제가 섞임. 마지막으로 틀린 뒤 다시 맞힌 문제만으로 위 조건을 채우면 그 상태로 오릅니다 |

답을 확인한 문제(답했거나 **모르겠어요**)는 문제·정답·해설을 **문제 은행**에 저장합니다. 풀기 전 문제의 정답은 저장하지 않습니다. 다음 문제를 만들 때 AI에 같은 개념에서 이미 푼 문제를 함께 보내 같은 문제가 반복되지 않게 합니다. 답을 확인한 뒤 문제 카드 오른쪽 위의 **신고** 버튼을 누르면 **문제가 이상해요** 창이 열립니다. 사유(정답이 틀린 것 같아요·문제가 애매해요·이 개념과 상관없어요·기타)를 고르고 이유를 적어 **제출하기**를 누르면 "정말 제출하시겠습니까?"를 한 번 더 묻습니다(기타는 이유를 꼭 적어야 합니다). 제출하면 그 문제의 응답은 개념 상태와 맞힌 횟수에서 빠지고 다음 문제를 만들 때 그 사유를 AI에 알려 같은 문제점을 피합니다.

해설을 본 뒤 다시 푼 문제, 도움 패널을 쓴 응답, 이미 푼 문제는 연습으로 기록해 맞힌 횟수와 다음 설명에 반영하고 상태는 올리지 않습니다. 틀렸다가 다시 맞히면 **실력이 늘고 있어요**로 표시합니다.

개념 카드의 **질문하기**는 세션 분석 화면에서는 오른쪽 도움 패널의 질문 탭을 엽니다. 내 지식·프로젝트 화면에서는 이 개념이 나온 분석 문서로 이동해 도움 패널을 그 개념의 질문 탭으로 엽니다. 답은 그 세션의 기록을 근거로 작성합니다.

도움 패널은 **이렇게 물어보세요**에 현재 개념·파일에 맞는 질문 예시를 표시합니다. 예시나 AI의 후속 질문을 누르면 바로 질문합니다. 같은 대상의 대화를 이어서 저장하며, 답변은 이전 대화·관련 장기 기억·개념별 설명 방침을 참고해 AI가 작성합니다. 답변의 **이번 답변에 참고한 내 학습 기록**에서 실제 제공한 기록을 확인할 수 있습니다. AI를 사용할 수 없으면 실패 사유를 표시하며 고정 답변을 반환하지 않습니다.

반복 질문은 예시를 보강하는 신호로, 최근 어려운 응답은 다시 설명할 신호로 사용합니다. **알고 있어요**는 짧은 상기로, **잘 모르겠어요**는 자세한 설명으로 이어집니다. **익히는 중**·**문제로 확인했어요** 카드에는 **잘 모르겠어요** 대신 **사실 아직 잘 몰라요**가 있습니다. 찍어서 맞혔거나 아직 헷갈리면 눌러 주세요. 카드가 **더 알아보는 중**으로 바뀌고 다음 설명이 더 자세해지며, 새 문제를 처음 풀어 답하면 다시 반영합니다. 설명 깊이·예시를 직접 선택하면 그 선택을 우선해 기억합니다. 질문·열람을 모른다는 증거로 바꾸지 않습니다. 개념 카드에는 설명을 조정한 이유를 표시하며, 프로젝트 사실과 위험 알림은 개인 상태로 바꾸지 않습니다.

## 읽는 사람 수준과 화면 설정

처음 사용할 때 **비개발자·입문·주니어·숙련** 중 설명 수준을 선택합니다. AI 문장은 수준별로 저장하며 이 선택을 이해 증거로 사용하지 않습니다. 글씨 크기·글꼴·밀도·라이트/다크 테마는 오른쪽 위 톱니바퀴에서 별도로 설정합니다.

## 작업 진행 상태

레포 위키, 주요 기능 분석, 세션 AI 분석·위키 보강, 내 지식 설명, 도움 답변은 **자료 확인 → AI 작성 → 저장 → 완료** 단계와 진행률을 보여 줍니다. AI 호출과 Supabase 읽기·쓰기를 구분하고, 단계에 따라 예상치를 갱신합니다. 시간으로 퍼센트를 늘리지 않으며 결과 저장을 마친 작업만 100%가 됩니다. 실패·취소는 완료와 구분합니다. 여러 AI 호출이 필요한 작업은 같은 단계에 오래 머무를 수 있습니다. 일반 화면 요청이 길어지면 화면 아래에도 데이터 요청 상태를 표시합니다.

테이블별 요청·실패·캐시 통계는 [Supabase 저장소 확인](deployment.md#supabase-저장소-확인)을 참고하세요.
